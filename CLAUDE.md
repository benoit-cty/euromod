# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A JRC (EU Joint Research Centre) expert-contract prototype that partially automates updating and validating **EUROMOD** fiscal parameters from legislation. The mission (see [00_project-overview.md](00_project-overview.md)): a temporally-aware, multilingual **RAG** over the fiscal legislation of 5 pilot member states → an **agentic workflow** that proposes structured parameter updates → a **validation UI** where a human accepts/rejects → an **evaluation pipeline** that scores the whole thing against a golden set.

**Naming:** the project codename is **Nómos**. Its four code subprojects are prefixed with their codenames on disk — `Nomotheca-RAG/` (legislation DB + ingestion, "Nomosync"), `Nomoscope-agentic-workflow/` (agentic pipeline + validation UI), `Nomokrisis-evaluation_pipeline/` (evaluation), `Nomergon-worker/` (the worker that executes every job) — kept alongside the original descriptive names for readability. The glossary is [CONTEXT.md](CONTEXT.md); decisions are in [docs/adr/](docs/adr/).

The numbered top-level docs (`00_`–`07_`) are the contract plan; `01_`–`05_` map to the five deliverable "Activities". Three code subprojects each implement one Activity and depend on each other in a line: **ingest → agentic-workflow → evaluation_pipeline**, all reading/writing one shared Postgres; the fourth, the worker, depends on all three and runs them.

## Architecture: one database, four Python packages, one worker, one desktop app

Everything centers on a single Postgres 17 + pgvector instance (see [docker-compose.yml](docker-compose.yml)):

- **`Nomotheca-RAG/ingest`** (`nomotheca-ingest`) — Activity 2. Archive-first legislation ingester. Fetches → snapshots → parses → chunks → loads the `legislation` DB, then builds BGE-M3 vector embeddings and translates non-English texts to English. Country-agnostic `core/` (~80%) + per-country adapters under `countries/<cc>/` (fetcher, parser, resolver). Adding a country is an adapter, not a rewrite; adapters are resolved via `countries/registry.py::get_adapter`. Library-first: the CLI and a future cache-miss workflow both call the same `ingest_citation` / `ingest_instrument` functions. Two source quirks are handled in the adapters: TAR never consolidates a never-amended act, so the LT adapter parses the Dokumentas row's own text as a `<id>/orig` version when the consolidation index is empty (the annual social-fund budget laws), and splits an act with no `straipsnis` — a Government resolution (nutarimas) or a ministerial order (įsakymas), where Lithuania sets the year's MMA, BSI, VRP, MVPD — into its numbered points, cited «2024 m. rugpjūčio 28 d. nutarimas Nr. 709 1 punktas» and keyed by `dokumento_id` (until 8 Nov 2026 they loaded as empty `istatymas` shells, and every MMA-based LT parameter was not_found with the resolution "ingested"); and BWB publishes some statutory formulas as PNG images (Participatiewet art. 22a), which the NL parser renders as `[formule als afbeelding: …]` — NL has no `reparse` path, refetch the act instead. Archive-first pays off through `cli reparse <CC> --url-like …`: after a parser change it replays the stored snapshot bytes through parser and loader without refetching (the FR parser now keeps Legifrance's NOTA application note — «applicables à l'imposition des revenus de l'année 2025» — as a trailing `NOTA :` paragraph, which is where a consolidated article says which income year it applies to); changed texts leave stale vectors for `embeddings build` to refresh. `cli rechunk [CC]` re-chunks stored texts whose chunks stop short of their content, with no fetch and no parse. An empty text gets no chunk (a (0, 0) chunk broke `chunks_check` and failed the whole act: the scout's ingests of loi 84-53 and of several KALI conventions in the 5 Nov run), and an id the DILA mirror answers 404 fails as such, not as a JSONDecodeError. A closed version ends where an already-loaded later version of the unit begins (`loader._chain_versions`): a KALI 2019–2023 text over a 2022 amendment, or a LEGI version «jusqu'au 1er janvier 2027» over one in force since 31 Oct 2026, broke `legal_unit_versions_no_overlap` and failed the act. Until 3 Nov 2026 the loader's count-based cut dropped the last chunk of every re-loaded text over 6 000 chars, 814 texts in all; follow it with `embeddings build`. See [Nomotheca-RAG/12_ingestion-architecture.md](Nomotheca-RAG/12_ingestion-architecture.md) for the shared/adapter boundary.
- **`Nomoscope-agentic-workflow/pipeline`** (`nomoscope-workflow`) — Activity 3. A deterministic step pipeline with **PydanticAI** LLM calls (not a free-roaming agent): `frame → retrieve → propose → critique → diff → enqueue`, one run per `(country, parameter, system year)` (`--year`; `--as-of` is a deprecated alias). `propose` and `critique` are the only LLM steps (PydanticAI structured output); everything else is deterministic code/SQL. Writes `ReviewItem` JSON to `data/queue/`. The **anti-hallucination rule is mechanical**: an LLM's `supporting_extract` must be found character-for-character inside the cited chunk or the critique fails. Export-first — nothing writes into EUROMOD files; a human accepts in the UI.
- **`Nomoscope-agentic-workflow/ui`** — Activity 3. **Tauri 2 (Rust) + Svelte 5** desktop validation UI. **It executes nothing and holds one credential, the analyst's own Postgres login** (ADR 0004). It reads the review queue from `params.review_queue` (loosely typed in Rust so the item schema can evolve pipeline-side), records decisions through `params.decide_review_item()` (one transaction: audit row + queue item), corrects a parameter's metadata (unit, source type, texts — never identity or values) through `params.edit_parameter()` (ADR 0005), submits every run (ingest, embed, translate, workflow, eval, impact) as a row in `ops.jobs` and polls `ops.job_events` for its log, gets query vectors for its semantic search from an `encode` job, and has a read-only Legislation page (search + library status) straight against the legislation DB. The layout is progressive disclosure: EUROMOD's own shell (a tab strip under the logo, a ribbon of grouped commands, the brand star `brand_background_EUROMOD.jpg` behind the pages, a status bar), an Overview home and five everyday tabs, technical tables/scores/logs/edit forms folded into `<details class="more">`, the Golden set, Evaluation, Impact and Jobs pages behind the ribbon's "Show expert tools" switch, and every enum shown through `src/lib/labels.js` (plain wording, raw value in the tooltip). The only file it ever writes is the EUROMOD export — the change set, one per country, through a folder picker.
- **`Nomoscope-agentic-workflow/rag-ui`** — a small Tauri 2 + Svelte 5 sibling of the review UI: chat with the corpus. Same rule as the UI (ADR 0004): each question is a `chat` job (priority 50) that the worker answers with `nomoscope-workflow chat` (`chat.py`, a PydanticAI agent with `search_legislation` = `retrieval.hybrid_search`, `find_article` = `locate_named_units`, `read_article`, and `web_search` = Tavily on the official portals of `scout.COUNTRY_SOURCES`). Every quote in an answer is verified against its chunk like a `supporting_extract` (one model retry, then flagged ✗); web results are leads only, and an act the corpus lacks is a *discovery* the analyst ingests with the normal `ingest` + `embed` jobs. Conversations are their `chat` jobs (`conversation_id` in the payload), so history is rows. It compiles the review UI's `jobs.rs`/`db.rs` in via `#[path]` rather than copying them. `mock/…` models give a key-less deterministic turn.
- **`Nomergon-worker`** (`nomergon`) — the worker. The only process that holds model credentials, loads BGE-M3, or reaches the internet. `nomergon serve` claims `ops.jobs` rows (`FOR UPDATE SKIP LOCKED`, one at a time, priority first) and runs each as a subprocess of the three CLIs above with `NOMOS_PYTHON=sys.executable` and `WORKFLOW_ENCODER=db`; stdout/stderr and `@progress {json}` lines become `ops.job_events`, a final `@result {json}` line becomes `ops.jobs.result`. The `encode` job type is answered in-process by a warm encoder on its own lane so the UI's search never waits behind an embedding build. It publishes the models it may use (`WORKER_MODELS`) in `ops.worker_models`; the UI offers that list and nothing else. Same image for JRC's deployment and the dev box (`docker compose --profile gpu up -d` starts it on the NVIDIA GPU; `--profile cpu` without one — a profile, so a plain `up` still works on a machine without the NVIDIA runtime; the cpu profile builds `nomergon-worker-cpu` from the same Dockerfile with `WORKER_VARIANT=cpu`, the CPU-only torch wheel and none of the ~4 GB of nvidia-* libraries). Nightly batches are `embed` / `translate` jobs submitted by hand for now; there is deliberately no scheduler yet. See [Nomergon-worker/README.md](Nomergon-worker/README.md).
- **`Nomokrisis-evaluation_pipeline`** (`nomokrisis-eval`) — Activity 4. Runs the agentic workflow (imported as an editable dependency) over a git-versioned golden set, scores KPIs with **pure deterministic code (no LLM judge)**, and stores results in an `eval` schema in the same Postgres, keyed by prompt/agent version, model, and language so per-language model comparisons (Activity 5) are a SQL view.

**Observability:** every LLM run is traced to **Arize Phoenix** (OTLP) at http://localhost:6006, storage in a `phoenix` DB in the same Postgres. Mock runs trace identically to real LLM runs. No LangSmith — `grep -ri langsmith` returns nothing by design.

**Data contract between the pieces:** the Activity 1 parameter JSON format ([Param_Schema/](Param_Schema/)). Ingest fills the legislation DB; the workflow's citations carry `jrc_database_id = chunks.id` with offsets into `unit_texts.content`; a golden case names its parameter by target (`euromod://…` or `group:<id>`) and carries an `expected` block. **Nothing runtime is a file**: the review queue, decisions, golden selections and cases, evaluation runs and job logs are all rows; inputs that stay in git are the EUROMOD enriched exports, the curation YAML overlays and the Country Report markdown.

## Running things

**Everything needs the stack up first** (from repo root):

```bash
docker compose up -d          # Postgres:5434 + pgAdmin:5050 + Phoenix:6006
                              # auto-applies Nomotheca-RAG/db/schema.sql, seed.sql, ops_schema.sql
docker compose --profile gpu up -d   # + the worker on the NVIDIA GPU (needs the container toolkit);
                                     #   --profile cpu on a box without one; or COMPOSE_PROFILES=gpu in .env
docker compose down -v        # full reset (schema re-applied on next up)
docker compose logs -f worker # what the worker is doing; `nomergon status` for workers + models
```

The worker needs the params and eval schemas too (`nomoscope-workflow init-param-db`, `nomokrisis-eval init-db`, idempotent). Roles for a shared deployment are in `Nomergon-worker/db/roles.sql` (worker role, `nomos_reviewer` group, one login per analyst; the dev stack keeps the single `jrc` superuser).

Postgres is on host port **5434** (not 5432, to avoid clashing with a local PG). Default DB URL: `postgresql://jrc:jrc@localhost:5434/legislation`. pgAdmin admin@euromod.eu / admin.

Python packages use **`uv`**. Run commands with `uv run` from inside each package dir:

```bash
# Ingest (Nomotheca-RAG/ingest)
uv run python -m nomotheca_ingest.cli tui                 # interactive Textual ingestion monitor
uv run python -m nomotheca_ingest.cli fr instrument JORFTEXT000051168007
uv run python -m nomotheca_ingest.cli country-report FR ../country_reports/Y16_CR_FR.md   # non-legislative corpus
uv sync --extra embeddings                              # manual path only: cli embeddings build --backend torch|openvino
                                                        # normally: `cd Nomergon-worker && uv run nomergon submit embed --wait` (only chunks lacking a vector)
uv sync --extra embeddings --extra translate            # manual path only: cli translate run --model openrouter/...
                                                        # normally: `nomergon submit translate --wait --payload '{"model": "…"}'` (worker holds the keys)

# Agentic workflow (Nomoscope-agentic-workflow/pipeline) — the worker runs these; a developer can too
uv sync
uv run nomoscope-workflow run-targets group:FR:tinkt_fr:tin_schedule 'euromod://FR/tin_fr/def_const/$tinrt_cdhr' --year 2025 --model mock/extractor
                                                        # records come straight from the params DB; one run = one system year
uv run nomoscope-workflow run-country FR --year 2025 --model mock/extractor   # every parameter of a country
uv run nomoscope-workflow queue                         # params.review_queue
uv run nomoscope-workflow export --out-dir /tmp/export  # the change set: one <CC>_changes.json per country

# Worker (Nomergon-worker) — in the container (`docker compose exec worker …`) or on the host
uv run nomergon serve                                   # claims ops.jobs; needs the GPU env
uv run nomergon submit embed --wait                     # nightly batches, by hand: embed, then
uv run nomergon submit translate --wait --payload '{"model": "azure_openai/gpt-5.6-luna", "target_lang": "en"}'
uv run nomergon jobs; uv run nomergon events <id> --follow; uv run nomergon cancel <id>

# Validation UI (Nomoscope-agentic-workflow/ui)
npm install
npm run tauri dev                                       # WSL: prefix LIBGL_ALWAYS_SOFTWARE=1
# RAG chat (Nomoscope-agentic-workflow/rag-ui) — same commands; Vite on :5174

# Evaluation (Nomokrisis-evaluation_pipeline)
uv run nomokrisis-eval init-db                             # create eval schema
uv run nomokrisis-eval import-golden                       # one-off: the git-era dataset/ + golden_sources/ into eval.*
uv run nomokrisis-eval build-openfisca-dataset --year 2025 --country FR  # draft cases from the OpenFisca corpus (selection in eval.golden_selections)
uv run nomokrisis-eval verify <case-id>                    # or the UI's "Golden set" tab (reviewer = current_user)
uv run nomokrisis-eval run --as-of 2025-06-01 --model mock/extractor   # offline smoke run (one progress line per case)
uv run nomokrisis-eval resume                              # continue an interrupted run, from eval.runs/run_cases/results
uv run nomokrisis-eval run-benchmark FR --year 2025 --model … --sample 20 --seed 1   # blind EUROMOD Y-1 -> Y over every parameter
uv run nomokrisis-eval benchmark-report <run-id>           # change matrix + OpenFisca arbitration
uv run nomokrisis-eval report
```

## Debugging a workflow run from a Phoenix trace id

Given a trace id (or "why did this run fail?"), use the **`/debug-phoenix-trace`** skill ([.claude/skills/debug-phoenix-trace/SKILL.md](.claude/skills/debug-phoenix-trace/SKILL.md)): it inspects the trace's spans straight in the `phoenix` DB inside the shared Postgres container, cross-checks corpus/embedding coverage in the `legislation` DB, and lists the known failure modes. Rule of thumb: most `not_found` runs are corpus problems (act not ingested, or ingested but not yet embedded), not LLM problems.

## LLM provider configuration

Models everywhere are **provider-prefixed strings**: `anthropic/…`, `openai/…`, `azure_openai/…`, `openrouter/…`, `together/…`, `jrc/…` (JRC's own OpenAI-compatible gateway: `JRC_LLM_BASE_URL` + `JRC_LLM_API_KEY`, a distinct prefix on purpose so a run on the internal gateway is never confused with OpenAI proper when models are compared), plus `mock/…` for key-less demos and deterministic tests. **Keys exist on the worker only**; an analyst picks from the list the worker publishes (`ops.worker_models`, from `WORKER_MODELS`) and never types a model string or holds a key. **Nothing in the pipeline knows the provider** — endpoint flexibility is a hard contractual requirement (Activity 5 compares multiple LLMs). The shared connection lives in [Nomoscope-agentic-workflow/pipeline/src/nomoscope_workflow/llm.py](Nomoscope-agentic-workflow/pipeline/src/nomoscope_workflow/llm.py); `nomotheca_ingest` and `nomokrisis_eval` both reuse it. For `azure_openai/<name>` the name after the slash **is the Azure deployment**; `AZURE_OPENAI_DEPLOYMENT` is only a default for a bare `azure_openai`, never an override — it used to be one, and every `azure_openai/*` run between 5 Aug and 8 Sep 2026 (terra, nano-2, Mistral, DeepSeek, sol…) silently ran on the `gpt-5.6-luna` deployment, judge included. Azure deployments named `gpt-*` / `o<digit>…` go through the **Responses API** (`llm.uses_responses_api`): on `/chat/completions` gpt-6-luna refuses function tools while reasoning — and structured output is a function tool — and on `/responses` it refuses `temperature`, so `llm.model_settings` is the one place request settings are built and drops it there; other Azure deployments (Mistral, DeepSeek) stay on chat completions. `manifest.json` now records `resolved_model` / `resolved_critique_model`; before comparing two runs as two models, check those differ and that Phoenix's LLM spans (`attributes->'llm'->>'model_name'`) agree.

**One config file: the repo-root `.env`** (template [.env.example](.env.example)). Every package's `load_config()` reads it and no other `.env`; the process environment wins; the worker container reads it through `env_file` and keeps the values it was **created** with — recreate it (`docker compose --profile gpu up -d worker`) after editing. `WORKFLOW_MODEL` is the one default: `WORKFLOW_CRITIQUE_MODEL`, `EVAL_BUILDER_MODEL` and `EUROMOD_TRANSLATE_MODEL` fall back to it (`EVAL_CRITIQUE_MODEL` unset = the model under test judges itself), and the worker publishes it first, then `WORKER_MODELS`, as the pickers' list. If keys live elsewhere, `set -a; source path/to/.env; set +a` before the command. See [.env.example](.env.example) for all knobs.

## Key constraints when changing things

- **The workflow is export-first and human-gated.** Never make the pipeline write back into EUROMOD parameter files; accepted values are exported, and only after a human Accept in the UI. A queue item is keyed `<country>_<target>_<system year>` (`queue_store.item_id`, the primary key of `params.review_queue`), so re-running a year replaces its review instead of piling up near-duplicates — the UI collapses the remaining per-year runs to one row and navigates between them in the detail panel. Reviewed queue items are immutable to re-runs (unless `--force`); `params.review_decisions` is append-only and is the system of record for human decisions. **A decision the DB refuses fails outright**: `store::prepare_decision` computes the updated item and the audit entry, then ONE call to `params.decide_review_item()` inserts the audit row and updates the queue row in the same transaction, with `reviewer = session_user` (inside a SECURITY DEFINER function `current_user` is the owner). Never split that into two statements or write the item first. There is no local copy of anything.
- **The export back to EUROMOD is a change set, and analysts' metadata edits are rows (ADR 0005).** `params.euromod_change_set` is the one definition both exports read (UI `<CC>_changes_<date>.json`, CLI `<CC>_changes.json`). Per changed parameter it holds the net metadata edits `{field: {from, to, …}}` and only the value rows a human accepted as `changed`/`new` or edited; no history, no accepted `unchanged`. A UI edit goes through `params.edit_parameter()` only (validates `KNOWN_UNITS`/`SourceType` in SQL — a pytest keeps the lists in step; refuses identity and values), is appended to `params.parameter_edits`, and is re-applied last by `ingest-params` and `curate-params`, so it wins over the export and the YAML.
- **The workstation executes nothing; the worker executes everything (ADR 0004).** Never add a process spawn, a model load, an API key read or a data directory to the UI. A new kind of work is a new `job_type` in `ops_schema.sql` + a payload model and argv in `nomergon/jobs.py` + a UI submit; a CLI that has a result prints one `@result {json}` line last. The reviewer role can read, decide, submit, cancel its own jobs and verify a golden case, nothing else (`Nomergon-worker/db/roles.sql`). Module-global latches (Tavily 432, `query_encoder._disabled`) are reset because each job is a fresh subprocess; do not move job execution in-process.
- **The verbatim-quote rule is mechanical, not prompt-only.** If you touch `propose`/`critique`, keep the character-for-character extract check against the cited chunk — it's the anti-hallucination guarantee.
- **Every instrument carries a source-trust class, and evidence retrieval excludes by class.** `instruments.source_trust_class` is `evidence` (legislation and statute-level acts), `guidance` (circulars, doctrine — citable, ranked equal, but shown as guidance on every proposal and counted in the eval) or `context` (never citable). Retrieval filters `source_trust_class <> 'context'` — never on an `instrument_type` string — and the class travels on every hit and citation. For a contributed document it is derived from the kind the reviewer states and never stated directly; "other" is guidance, so an unnamed document cannot be granted statute-level trust by accident. See [docs/adr/0001-guidance-is-citable-evidence-with-a-visible-class.md](docs/adr/0001-guidance-is-citable-evidence-with-a-visible-class.md).
- **Collective agreements are evidence, like the law** (ADR 0006). Where the social partners set a rate (FR AGIRC-ARRCO: ANI du 17 novembre 2017 art. 37, APEC, cadres' prévoyance), the agreement is the source of truth: `instrument_type='collective_agreement'`, class `evidence`. FR reads them from DILA **KALI** as source `FR-KALI` (`cli instrument fr KALITEXT…/KALIARTI…`). KALI exists only as dumps, so the adapter keeps a local copy under `NOMOTHECA_KALI_DIR` (worker volume `kali-cache`, ~1.8 GB), kept current by `cli kali-sync` (an ingest syncs on its own after 12 h), and archives each document as DILA JSON so the LEGI parser and `reparse` apply. The scout keeps `KALITEXT`/`KALIARTI` ids and refuses `KALICONT` (a whole convention). Contributed documents have a `collective_agreement` kind in every country. Board decisions that are not agreements (the AGS rate) are not covered.
- **The scout fetches guidance from listed publishers, always as guidance.** Some values are published by an administration, not in any act (the Cnav circular gives the ASPA/ASI ceilings after the 1 April revaluation). `scout.GUIDANCE_PUBLISHERS` lists, per country, the publisher's domain, its fixed kind (FR: Cnav and Unédic `circulaire`, BOFiP `doctrine`) and a URL pattern for one document, which also gives the title and the validity date. No full date in the URL means no ingest. The model only writes `guidance_queries`, searched on those domains. A matching URL is ingested with `cli document … --kind <fixed> --trigger cache_miss`. An ingest test checks that every publisher kind maps to guidance, so a web-discovered document can never become evidence. In a `numbered` document, a heading must start with a letter after its number (a table row «19 212,03 € 1 601 €» is not section 19), and the numbered paragraph stays in its unit's content; a bare count with almost no body before a sibling heading is a table row, not a heading (`documents.drop_table_rows`: «1 enfant 0,0619% 0,0516%» … made ten 25-character sections of the Caf EAJE barème, cut off from the column headers), and bare numbers that start over are footnotes: only a first run reaching 2 numbers sections (Agirc-Arrco circular 2024-18 reads 1 | 1 2 3 | 1, and its 2025 rate table was a section opening on the footnote «1 Plafond de sécurité sociale.»; all 130 FR documents were reparsed and re-embedded on 7 Nov). After a parser change, `cli reparse-documents [-j CC] [--title-like …]` rebuilds contributed documents from their stored snapshot (units replaced, instrument and declaration kept; then `embeddings build`). Every unit's citation is unique: the loader matches units by citation, and before 6 Nov 2026 a column header repeated over several tables («0 à 3 ans 3 à 6 ans», now a table row, as is any section numbered 0) made the sections share one citation and keep only the first text — DSS/2B/2025/38 lost its ASF, complément familial and ARS amounts, 40 Cnav circulars and BOFiP barèmes lost text; all 119 FR documents were reparsed on 6 Nov. A contributed `.pdf` URL that answers httpx with an HTML page is retried once in headless Firefox (`contributed.fetch_in_browser`, optional `browser` extra; the worker image installs Firefox): sante.gouv.fr serves its Bulletin officiel — instructions DSS/2B/2025/38 (BMAF) and DSS/2B/2024/181 (family-benefit ceilings) — to a browser and a «Vérification de sécurité» page to a script; a page that wants a human is left to the human, and when no browser gets the PDF the ingest is refused, never fed the HTML page (the AGS 2025 rate PDF answered with the press-release listing, ingested as the release). A scanned PDF has no text layer and there is no OCR: contribute a Markdown transcription instead (the ANI APEC du 12 juillet 2011, art. 14: 0,036 / 0,024 pour 100).
- **Country Reports are context, never evidence.** EUROMOD Country Reports are ingested with `instrument_type='country_report'` and `source_trust_class='context'`; Nomoscope's evidence retrieval SQL excludes them by that class (see the rule above), and `retrieval.country_report_search()` is the only sanctioned way to read them (query framing, UI display). Never let `propose`/`critique` cite a CR chunk — the CR describes the model, so citing it as support is circular.
- **`national_team_source` values route around the pipeline** and are never overwritten — not every EUROMOD parameter is legislation-derivable.
- **Regional acts are child jurisdictions, and retrieval is scoped by the parameter's region** (ADR 0003). Spain's autonomous-community acts are filed under `ES-AR`, `ES-CN`, … (`jurisdictions.parent_id = ES`, seeded from one table in `Nomotheca-RAG/ingest/src/nomotheca_ingest/countries/es/regions.py`; existing databases run `db/migrations/0002_es_autonomous_communities.sql`). Evidence retrieval filters on a jurisdiction *scope* — `[country]` for a national parameter, `[country, region]` for a regional one, the region read off the constant's NUTS-2 digits by `regions.region_key` (`$bsarg_rg24_*` → `ES24` → `ES-AR`) — never on the whole tree: Aragón's parameter must not be "supported" by a verbatim quote from Asturias's decree, a false positive the extract check cannot catch. Regional citations are qualified by region (`Ley 3/2021 Asturias Artículo 14`; Aragón has a Ley 3/2021 too), and `EsResolver` refuses a bare regional number. BOE consolidates the communities' framework laws but not their annual budget laws, where the current amounts live — see `.scratch/es-autonomous-communities/`.
- **Percent literals are scalars in the store, and units outside the export vocabulary exist on purpose.** `paramdb.normalise_value` reads EUROMOD's `8.17%` as 0.0817 (the `/1` form the curated rates use) — before 8 Sep 2026 every NL/LT rate was stored as null and a correct proposal could only route `changed`. `KNOWN_UNITS` also accepts `currency/hour` (the SMIC is legislated per hour), `/100` (a rate held in percentage points: FR `$bho_rl_rate2` = 0.45 for «0,45 %»; the proposer keeps the points and the range check is ±100) and `ratio` (a multiplier above 1, e.g. NL `$bfa_mult2`, which the `/1` range check would reject). A bracket-schedule group has no text of its own in the export: `load_group_record` composes its label/description from the members, otherwise the frame query degenerates to `ES Tax schedule`; it composes a law-language label/description from the members' `parameter_texts` too, and the frame step searches with those alone (in English, the FR AGIRC-ARRCO schedules never reached the Agirc-Arrco circular stating «3,15 % … 8,64 %»). Re-run `ingest-params` + `curate-params` whenever the enriched export changes — FR/IE/LT ran for a month on the August export after the September one landed.
- **A derived value is arithmetic over quoted operands, checked like an extract.** When no extract states the value but the extracts state what it is computed from (NL `$bfa_mult2` = 347.83/286.45, a base plus a statutory increment, hourly rate × statutory hours), the proposer may set `derivation` + `operands`; `pipeline._check_derivation` verifies every operand's `supporting_extract` character-for-character in its cited chunk, that the extract states the operand's figure (digits, a number the law spells out — «trois fois ce plafond», «la moitié» — or, for a multiplier above 1, its increase — «majoré de 50 %» states 1.5; a PDF table row «I 329,71 397,64 449,43 65,21» states each of its four amounts, while «1 801,80» stays one number — and an operand whose extract misses its figure gets, in the retry feedback, the chunk's sentence that does state it), that the expression uses only `+ - * /`, operand names, `DERIVATION_CONSTANTS` (1, 2, 3, 4, 6, 9, 12, 13, 52, 100, 365, 366, 1000 — 3/6/9 as the months either side of a mid-year revaluation; a remembered 151.67 is rejected) and `round(x, n)` with `n` an integer literal 0–8, rounding half-up as legal texts do (AGIRC-ARRCO art. 36 «arrondis au centième»: 6,20 % × 127 % → 7,87 %), and that it evaluates to `value_scalar`. A verified currency derivation is then rounded half-up like the value held (`pipeline._round_like_held`: whole units when EUROMOD holds an integer, else cents; a `/1` rate held with 4–8 decimals to as many — 12,954 % → 0.1295 — a coarser rate never, since 0.0675 is a real change from 0.068) — the law states the operands, the administration publishes the rounded amount (29 169 × 1,8 = 52 504,2 → 52 504), and the rounding rule is rarely in the corpus; the reviewer sees a `note:`. Where a precision applies, the rounded figure is the derivation's own result, not the figure the model typed: the check accepts a result within 0.1 %, and RSA 646,52 × (1,28412 + 2 × 0,42804) = 1 383,68 was typed and accepted as 1 383,28. With no precision to round to (a coarse rate, a ratio) the result itself is proposed, and a schedule — whose figures are not replaced — must contain the result exactly (`round(x, n)` states a rounding): the typed figure never reaches the queue. Each operand becomes its own `Reference`; the queue item carries the `derivation` summary. Never let a bare figure through unquoted — that is the hallucination channel the rule closes.
- **An "FYA" amount is proposed as the amount in force, never averaged.** EUROMOD labels many amounts "FYA" (full-year average) yet holds the April amount (prime d'activité 949.82 = 633,21 × 1,5), and where it holds «(a*9+b*3)/12» the scorer accepts the point value; `prompts._average_note` tells proposer and critique so whenever the label/description mentions an average or the held value is such a formula.
- **Confirming the held value is not blocked by its date.** When a proposal's scalar equals the value EUROMOD holds and the critique accepts the citation, its `dates_consistent` objection becomes a `note:` (`pipeline._confirms_held`) — the start date of an unchanged value changes nothing in the export. The mechanical date checks still apply.
- **A system year is the whole year.** For an `in_force` parameter, retrieval adds up to `retrieval.LATER_MAX_HITS` versions entering into force after the 1 July reference date and by 31 December (`method="later_in_year"`, marked in the prompt; `locate` does the same), and the critique accepts a `valid_from` up to year end when it cites one. That later search runs `LATER_DEPTH` (4) times deeper than k before keeping the versions that start after 1 July — a December act competes with every text in force (the 2025 prime-de-Noël décret, in force 14 December, was never in the top k). The frame query of a law-language text keeps its «…» and (…) spans (`pipeline._keep_span`: they hold the benefit's name — «prime de fin d'année», «(Revenu de Solidarité Active)»; 472 of 1 277 FR texts have them) and drops only English EUROMOD comments and spans left with no word; an English record drops them as before. The 2025 chèque énergie barème is the arrêté du 31 juillet 2025 («à compter du 1er janvier 2025»): filtered on 1 July, all 17 `bhoey_fr` parameters were not_found with the arrêté in the corpus.
- **A code article is held with its recent versions, and its cross-references are followed.** DILA mints one id per article version; the FR parser queues every version in force since `VERSION_HISTORY_FROM` (2023-01-01) from the article's `VERSIONS` block — CGI art. 32 was held only as amended in Feb 2026, and 30 FR code articles had no 2025 version (backfilled 4 Nov 2026, 284 versions). `retrieve` (and `locate` after a not_found) follows `retrieval.cross_referenced_articles`: an L. article's first same-chapter R./D. articles and the articles a retrieved article names (R. 531-1 → R. 522-2, the PAJE 25 %/30 % per-child rule), two hops, one query per hop; a non-code act's reference counts when it names the code in the same sentence («l'article L. 531-3 du code de la sécurité sociale» in the arrêté fixing the ceilings — without R. 531-1 in view the critique rejected PAJE ceilings as «using the complément familial's rule»). References are also followed backwards (`retrieval.implementing_acts`): for the 20 best-ranked code articles, the non-code act versions in force on the reference date, entered into force in the year before it, that name that article of that code (also as one of a list the code closes, «Articles L. 381-1, …, R. 522-2 … du code de la sécurité sociale»), ranked by distance to the query before the cap of 6 (in retrieval order the six family-benefit articles of «RSA, increment per additional child» filled it, and CASF L. 262-2 was the 16th), the 6 nearest acts each bringing its 2 chunks nearest to the query as well — an instruction names its articles in «Textes de référence» and states the figures sections later — CASF L. 262-2 «fixé par décret» → the décret du 28 mars 2025 setting the RSA at 646,52 € (never later in the year: the 26 Dec 2025 arrêté naming L. 531-2 is the 2026 PAJE barème). An article's references to its own act («l'aide mentionnée à l'article 1er», not followed by another act's name) are followed too (`retrieval.same_act_articles`, in `retrieve` after the later-in-year versions and in `locate`), in the version in force when the citing article starts — décret n° 2025-1212 art. 2 states 152,45 €, art. 1 names the ASS, both enter into force in December; without art. 1 the four prime-de-Noël amounts were not_found. Backwards too, outside codes (`retrieval._same_act_citing`): the same act's articles that name a retrieved one, nearest article number first, two per article — ANI AGIRC-ARRCO art. 36 «un pourcentage d'appel, fixé à 127 %, est appliqué aux taux visés à l'article 35»; with art. 35 alone the schedules were refused for want of the call rate. A schedule may derive one of its figures (the result must equal a threshold, rate or amount of the proposal), and the `/1` range is [-1, 1] (negative rates exist).
- **The scout's second leg looks the named source up in the corpus we hold.** Six of nine "corpus gap" refusals on the 2026-09-09 eval named acts already ingested (LIRPF art. 66, Wet IB 2001 art. 2.10, CSS D633-3, Finance Act 2024) that the framed query ranked below k. `retrieval.locate_named_units` resolves the proposal's `missing_sources` (act by title trigram similarity, article by number in `legal_units.citation`, else FTS inside the named act; and the need's words ranked over the texts entered into force in the year before the reference date — filling the slots when nothing found is that recent, three extra slots otherwise — «l'arrêté portant revalorisation … de la BMAF» matches the 2005 decree by title, the 2025 amount is in instruction DSS/2B/2025/38) and the `locate` step feeds those chunks to the retry, whether or not the scout ingested anything; they carry `method="located"` and the ScoutResult lists them under `located`. Web discovery needs Tavily; on HTTP 432 (plan quota spent — the whole 2026-09-09 eval ran that way) the scout says so once and skips further web calls.
- **A mistyped `citation_chunk_id` is resolved by its extract, never guessed.** The critique rewrites an id that is not among the retrieved chunks to the ONE retrieved chunk containing the `supporting_extract` character-for-character, else to the ONE retrieved chunk whose citation is the string the model wrote in the id field (`pipeline._resolve_chunk_id`) — so a misquote of it still gets the passage in its retry feedback instead of a bare "not retrieved"; two candidates keep the mechanical failure. A cited id that IS retrieved but does not hold the quote is re-pointed to the ONE other retrieved chunk that does (`pipeline._repoint_misquoted`, main citation and operands): the model swaps ids between retrieved chunks, and eleven right values of the 5 Nov run were refused for it. Derivation operands get the same resolution (11 derivations of the 3 Nov run cited a citation string or a corrupted UUID). A failed quote's retry feedback quotes the passage it was trying to copy (`retrieval.closest_passage`) — the model "tidies" legal French and, told only "not verbatim", repeats it. A proposal refused for nothing but misquotes (main extract or operands) gets one attempt past `MAX_PROPOSAL_ATTEMPTS` (`pipeline._misquoted_only`): the attempt after `locate` is otherwise the last, and the RSA forfait logement «calculé pour trois personnes ou plus lorsque» was refused with the right passage in its feedback. The verbatim guarantee is unchanged — the extract is still checked against the chunk it now points to. `retrieval.verify_extract` treats whitespace runs as equal, and whitespace between two *letters* as absent (a PDF's split ligature: «prestati ons» in instruction DSS/2B/2025/38 failed every quote of the BMAF sentence); between digits it is never ignored. Punctuation at a quote's two ends is not checked either (the model closes «… deux personnes ; 3° A 16,5 %» on a full stop).
- **The parameter store is the source; nothing is materialized to disk.** `extracted_parameters/enriched/<CC>.enriched.json` is the EUROMOD-delivered ground truth and is read-only; everything else the DB needs arrives through the same `ingest-params` + `curate-params` path — the curation overlay `Nomoscope-agentic-workflow/pipeline/curation/<CC>.curation.yaml` carries what the export lacks or gets wrong (`temporal_basis`, `source_type`, and `unit`: the FR export labels all 146 `*rate*` parameters `currency`, IE 48 and LT 54 rate-like parameters likewise, all curated to `/1` — membership by value, every year's value a fraction — because the prompt's percent normalisation and the critique's range check key on it), re-applied after every `ingest-params` — `extracted_parameters/curated/<CC>.in_function.json` for parameters EUROMOD defines inside functions (the connector cannot export them; FR CDHR), and the export's own `groups` block for bracket schedules, reassembled into one record by `paramdb.load_group_record` (FR barème = `FR:tinkt_fr:tin_schedule`). `run-targets` and a golden case load the record straight from the DB (`paramdb.load_record` / `load_group_record`) — never let a run or a golden case depend on a hand-authored parameter file.
- **The golden set is rows, keyed by content hash.** `eval.golden_selections` holds what `golden_sources/<cc>.json` used to (header + entries, per country and kind), `eval.golden_cases` the built cases with the verdict in columns (`verified`, `reviewed_by = current_user`, `reviewed_at`, `review_note`) so the reviewer role can be granted exactly those; a rebuild keeps a verdict only while the ground truth is unchanged. Every eval run records the **golden set hash** of the cases it froze in `eval.run_cases`, and resumes from `eval.results`; there is no `.eval_runs/` and no `manifest.json`. The git-era files under `dataset/`, `dataset_embedding/`, `golden_sources/` are imported once by `nomokrisis-eval import-golden` and then retired.
- **Golden readiness follows the value-bearing citation, and a golden citation list is any-of.** `citation_correct`/`retrieval_hit` accept any listed citation, so list every article a correct pipeline may cite (the finance act AND the consolidated code article; the by-reference rule AND the act stating the amount). An OpenFisca reference titled «(seuils avant revalorisation)» is the pre-indexation base article and does not make a case `corpus_available` (the year's amount is in a ministerial letter with no Legifrance id); a selection entry may set `corpus_available` explicitly in both builders. `score_item` completes a bare proposed scalar with the stored value's `#period` suffix before comparing, so `747#m` against a parameter EUROMOD holds as `8964#y` is a cross-period match, not a miss.
- **OpenFisca corroborates, it never evidences.** The ingested OpenFisca corpus (`params.external_*`, commit-pinned) is a *curated secondary source*: it can suggest links (`nomoscope-workflow match-openfisca` → `params.parameter_links`, suggestions until `validated_by` is set) and draft evaluation ground truth (`nomokrisis-eval build-openfisca-dataset` → `verified: false` cases reviewed in the UI's Golden set page, under expert tools), but it can never be a `supporting_extract` for a proposal. Golden cases re-derive the expected value from the parameter's `temporal_basis`, not from the link's year alignment: `income_year` → the OpenFisca value keyed `<system year>-01-01` (the same income-year convention the pipeline back-dates to), `in_force` → the value in force at `as_of`. OpenFisca stores change points only, so "the value at D" is always the latest entry at or before D.
- **`temporal_basis: income_year` parameters (FR income-tax family) are searched under the law's income-year label.** EUROMOD system year Y holds the schedule enacted by the finance act for Y and applies it to the incomes of Y (FR_2025: loi n° 2025-127, the PLF 2025, on 2025 incomes); French law and OpenFisca label that same schedule by the income it is legally assessed on, one year earlier («impôt 2025 sur les revenus 2024»). So **for system year Y the value is in the text the law labels "income Y−1"** — a rule for finding the text, not a statement about which incomes EUROMOD taxes; the mapping lives in exactly one place, `schema.income_year_for` (offset `INCOME_YEAR_OFFSET = -1`), and four things derive from it: retrieval/scout target 1 July of the year *after* the income year, proposals back-date `valid_from` to the income-year start, the critique's budget-act window opens 1 December of the income year (older versions route `provisional` — Accept is blocked in the UI; distinct from `not_found` — **unless** the cited text is a consolidated code article in force on the retrieval date with a corpus snapshot at least that fresh: that is the text the assessment of income year Y applies, however old its version start — CGI art. 197 «en vigueur du 16 février 2025 au 21 février 2026» is the 2024-income barème, art. 223 sexies has read the same since 2018 — decided by `pipeline._consolidated_in_force`, guarded against a text whose application note names the *next* income year), and golden cases read the OpenFisca entry at `income_year_for(year)-01-01`. Never re-derive `as_of.year ± 1` at a call site. A third basis, `start_of_year`, is for parameters EUROMOD holds at their 1 January value (`schema.start_of_year_as_of`): retrieval, the critique's date check and the prompt use 1 January of the system year, and no later-in-year version is added — FR `$tpr_threshold*` (CGI 1417 is revised each June), `$UB_dayfixamt` (each 1 July), `$tscerui_rate1`, `$bsawk_income_rate`, each proven on EUROMOD's own history (a change in year Y first appears in system year Y+1). Note the FR Country Report's Table 2.77 heads its column "Taxation 2025 (income 2025)" — that label is wrong as a statement of French law: its values are the barème for 2024 income (taxation 2025, LF 2025). It is only true in the sense that EUROMOD applies them to 2025 incomes. The flag itself is curated (JSON `information` block + `params.parameters.temporal_basis`, preserved by re-ingest) — never derive it from the export, and don't let legal in-force dates in the legislation DB be rewritten to compensate.
- **Value scoring must normalise, not string-match.** EUROMOD stores mid-year changes as weighted averages, ~75% of FR params as formula strings (`$PSS * 4`), and period suffixes (`#m #y …`) with fixed conversion factors. Implemented in `nomokrisis_eval.scoring.normalise_value` / `values_equal`: formulas evaluated, `$const` refs resolved via a constants map, cross-period comparison on the monthly basis, relative tolerance 1e-9 — float noise only (it was 1e-6 until 8 Nov 2026, which equated 52 504,00 and 52 504,05); a schedule band with no rate equals a 0 % band (the CEHR's first band has no rate member). There is no tolerance beyond that, on purpose: when EUROMOD is one cent or one euro off the figure the law states, the case is a **finding** (`CaseResult.euromod_discrepancy`, `scoring.law_vs_euromod`) — the proposal passed the critique with a verbatim extract, every figure where it parts from EUROMOD is exactly one unit of the held precision (0.01 on a cents amount, 1 on a whole one; a rate never), and the figure is in the quoted extract (`stated`) or the result of a verified derivation (`derived`, which also rests on `_round_like_held`). `value_correct` stays False; the benchmark report gives it its own column («EUROMOD off the law») and headline line, and a `success` line that adds findings to correct answers — finding where EUROMOD departs from the law is what the project is for (AF 151.81 vs 151,80 €, the barème's 11 496 vs 11 497). See the detailed "what we can/cannot do" findings at the bottom of [Nomokrisis-evaluation_pipeline/README.md](Nomokrisis-evaluation_pipeline/README.md).
- **Embeddings are normally an `embed` job, not a hand-run command.** After an ingest, `reparse`, `rechunk` or translation, `uv run nomergon submit embed --wait` (in `Nomergon-worker`; payload `model_id`, `batch_size`, `limit`, `dry_run`, `precision`, `authentic_only`) embeds exactly the chunks with no vector for that model, on the worker's GPU. The `cli embeddings build` commands below are the manual path (no worker, debugging, `--in-force-on` comparison builds); never run one while the worker is embedding or an eval is running — one GPU.
- **Embeddings on the target workstation (Intel Ultra 7 265H) prefer OpenVINO over ONNX** on the local CPU path. On the NVIDIA box (GTX 1080 Ti) OpenVINO is not an option at all — its GPU plugin is Intel-only — so that machine runs `--backend torch` on CUDA from a separate environment (`UV_PROJECT_ENVIRONMENT=.venv-cuda uv sync --extra embeddings-cuda`, cu126 wheels because Pascal is sm_61, fp32 because Pascal fp16 is 1/64 rate). The default `.venv` stays CPU+OpenVINO so the UI and `scout.py` keep working. BGE-M3 with the `fix_mistral_regex` flag is a known breakage — leave it off (details in [Nomotheca-RAG/ingest/README.md](Nomotheca-RAG/ingest/README.md)).
- **The embedding model is a registry id, and a query must be encoded by the model that embedded the corpus.** `nomotheca_ingest/core/embedding_models.py` is the one list (1 = BGE-M3, the default; 2 = Qwen3-Embedding-0.6B, 5 = Arctic-Embed-L v2, …; 99 stays the in-SQL placeholder): each model's vectors live under its own `embeddings.model_id` in the one `halfvec(1024)` column (Matryoshka truncation above 1024, zero-padding below), and its query prompt lives there too — `SentenceTransformerBackend.encode_queries` applies it, `query_encoder.encode(query, url, model_id)` and the worker's encode lane (`model_id` in the payload) route to it. Compare models with `embeddings build --model <key> --authentic-only --in-force-on …` then `nomokrisis-eval build-embedding-cases` (golden cases → retrieval cases with the `frame` step's own query, `pipeline.frame_query`), `run-embeddings --embedding-model-id N`, `compare-embeddings`. A vector query that orders by `embedding <=> q` next to filters walks the HNSW index and filters the 40 global nearest afterwards (2 rows out of 15 for LT): rank inside a window function or by a computed score, as `retrieval._VEC_CTE_QVEC` and `embedding_eval.vector_search` do.
