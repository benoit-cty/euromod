# CLAUDE.md

## What this repo is

A JRC (EU Joint Research Centre) expert-contract prototype that partially automates updating and validating **EUROMOD** fiscal parameters from legislation. The mission (see [docs/00_project-overview.md](docs/00_project-overview.md)): a temporally-aware, multilingual **RAG** over the fiscal legislation of 5 pilot member states → an **agentic workflow** that proposes structured parameter updates → a **validation UI** where a human accepts/rejects → an **evaluation pipeline** that scores the whole thing against a golden set.

**Naming:** the project codename is **Nómos**. Its four code subprojects are prefixed with their codenames on disk — `Nomotheca-RAG/` (legislation DB + ingestion, "Nomosync"), `Nomoscope-agentic-workflow/` (agentic pipeline + validation UI), `Nomokrisis-evaluation_pipeline/` (evaluation), `Nomergon-worker/` (the worker that executes every job) — kept alongside the original descriptive names for readability. The glossary is [CONTEXT.md](CONTEXT.md); decisions are in [docs/adr/](docs/adr/).

The numbered docs in `docs/` (`00_`–`07_`) are the contract plan; `01_`–`05_` map to the five deliverable "Activities". Three code subprojects each implement one Activity and depend on each other in a line: **ingest → agentic-workflow → evaluation_pipeline**, all reading/writing one shared Postgres; the fourth, the worker, depends on all three and runs them.

## Architecture: one database, four Python packages, one worker, one desktop app

Everything centers on a single Postgres 17 + pgvector instance (see [docker-compose.yml](docker-compose.yml)):

- **`Nomotheca-RAG/ingest`** (`nomotheca-ingest`) — Activity 2. Archive-first legislation ingester. Fetches → snapshots → parses → chunks → loads the `legislation` DB, then builds BGE-M3 vector embeddings and translates non-English texts to English. Country-agnostic `core/` (~80%) + per-country adapters under `countries/<cc>/` (fetcher, parser, resolver). Adding a country is an adapter, not a rewrite: a `countries.base.BaseAdapter` subclass (it also declares the country's `contributed_kinds`), resolved via `countries/registry.py::get_adapter`. Library-first: the CLI and a future cache-miss workflow both call the same `ingest_citation` / `ingest_instrument` functions. Per-country source quirks (LT, ES, IE, NL), `reparse`/`rechunk` and the loader rules are in [Nomotheca-RAG/CLAUDE.md](Nomotheca-RAG/CLAUDE.md). See [Nomotheca-RAG/12_ingestion-architecture.md](Nomotheca-RAG/12_ingestion-architecture.md) for the shared/adapter boundary.
- **`Nomoscope-agentic-workflow/pipeline`** (`nomoscope-workflow`) — Activity 3. A deterministic step pipeline with **PydanticAI** LLM calls (not a free-roaming agent): `frame → retrieve → propose → critique → diff → enqueue`, one run per `(country, parameter, system year)` (`--year`; `--as-of` is a deprecated alias). `propose` and `critique` are the only LLM steps (PydanticAI structured output); everything else is deterministic code/SQL. Writes each `ReviewItem` as a row of `params.review_queue`. The **anti-hallucination rule is mechanical**: an LLM's `supporting_extract` must be found character-for-character inside the cited chunk or the critique fails. Export-first — nothing writes into EUROMOD files; a human accepts in the UI.
- **`Nomoscope-agentic-workflow/ui`** — Activity 3. **Tauri 2 (Rust) + Svelte 5** desktop validation UI. **It executes nothing and holds one credential, the analyst's own Postgres login** (ADR 0004). What it reads and writes, and its layout: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **`Nomoscope-agentic-workflow/rag-ui`** — a small Tauri 2 + Svelte 5 sibling of the review UI: chat with the corpus. Same rule as the UI (ADR 0004): each question is a `chat` job (priority 50) that the worker answers with `nomoscope-workflow chat` (`chat.py`, a PydanticAI agent with `search_legislation` = `retrieval.hybrid_search`, `find_article` = `locate_named_units`, `read_article`, and `web_search` = Tavily on the official portals of `scout_sources.COUNTRY_SOURCES`). More in [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **`Nomergon-worker`** (`nomergon`) — the worker. The only process that holds model credentials, loads BGE-M3, or reaches the internet. `nomergon serve` claims `ops.jobs` rows (`FOR UPDATE SKIP LOCKED`, priority first) into `WORKER_CONCURRENCY` parallel slots (default 3) — `embed`, `translate`, `translate-params` one of each at a time (shared backlog), and every `embeddings build`, the scout's included, takes a Postgres advisory lock so one model build uses the GPU at a time — and runs each as a subprocess of the three CLIs above with `NOMOS_PYTHON=sys.executable` and `WORKFLOW_ENCODER=db`; stdout/stderr and `@progress {json}` lines become `ops.job_events`, a final `@result {json}` line becomes `ops.jobs.result`. The `encode` job type is answered in-process by a warm encoder on its own lane so the UI's search never waits behind an embedding build. It publishes the models it may use (`WORKER_MODELS`) in `ops.worker_models`; the UI offers that list and nothing else. Same image for JRC's deployment and the dev box (`podman-compose --profile gpu-cdi up -d` starts it on the NVIDIA GPU as `nomergon-worker-cdi`, through CDI; Docker's equivalent is `docker compose --profile gpu up -d`, service `worker`; `--profile cpu` without one — a profile, so a plain `up` still works on a machine without the NVIDIA runtime; the cpu profile builds `nomergon-worker-cpu` from the same Dockerfile with `WORKER_VARIANT=cpu`, the CPU-only torch wheel and none of the ~4 GB of nvidia-* libraries). Nightly batches are `embed` / `translate` jobs submitted by hand for now; there is deliberately no scheduler yet. See [Nomergon-worker/README.md](Nomergon-worker/README.md).
- **`Nomokrisis-evaluation_pipeline`** (`nomokrisis-eval`) — Activity 4. Runs the agentic workflow (imported as an editable dependency) over the golden set held in `eval.*` rows, scores KPIs with **pure deterministic code (no LLM judge)**, and stores results in an `eval` schema in the same Postgres, keyed by prompt/agent version, model, and language so per-language model comparisons (Activity 5) are a SQL view.

**Observability:** every LLM run is traced to **Arize Phoenix** (OTLP) at http://localhost:6006, storage in a `phoenix` DB in the same Postgres. Mock runs trace identically to real LLM runs. No LangSmith — `grep -ri langsmith` returns nothing by design.

**Data contract between the pieces:** the Activity 1 parameter JSON format ([Param_Schema/](Param_Schema/)). Ingest fills the legislation DB; the workflow's citations carry `jrc_database_id = chunks.id` with offsets into `unit_texts.content`; a golden case names its parameter by target (`euromod://…` or `group:<id>`) and carries an `expected` block. **Nothing runtime is a file**: the review queue, decisions, golden selections and cases, evaluation runs and job logs are all rows; inputs that stay in git are the EUROMOD enriched exports, the curation YAML overlays and the Country Report markdown.

## Running things

The root [Makefile](Makefile) wraps the everyday commands (`make` lists them: `up-gpu`/`up-cpu`, `update COUNTRY= YEAR=`, `ui`, `rag-ui`, `translate`, `embed`, `batch`); every model-running target submits a job inside the worker container.

**Everything needs the stack up first** (from repo root):

```bash
podman-compose up -d          # Postgres:5434 + pgAdmin:5050 + Phoenix:6006
                              # auto-applies Nomotheca-RAG/db/schema.sql, seed.sql, ops_schema.sql
podman-compose --profile gpu-cdi up -d   # + the worker on the NVIDIA GPU (CDI: needs `nvidia-ctk cdi generate`);
                                         #   --profile cpu on a box without one
podman-compose down -v        # full reset (schema re-applied on next up) — deletes the database
podman logs -f nomergon-worker-cdi   # what the worker is doing; `nomergon status` for workers + models
podman exec nomergon-worker-cdi /app/.venv/bin/nomergon status   # the worker's CLIs live in /app/.venv/bin
```

**Podman is the default engine** ([docs/podman.md](docs/podman.md)): `podman` + `podman-compose`, the GPU worker is the CDI service `worker-cdi` (profile `gpu-cdi`, container `nomergon-worker-cdi`; the CPU one is `nomergon-worker-cpu`). The Makefile picks Podman when it is installed, else Docker (`ENGINE=docker` to force). **Docker** remains supported for a future deployment ([docs/docker.md](docs/docker.md), with a command translation table): `docker compose`, the GPU worker is the service `worker` (profile `gpu`, container `nomergon-worker`, `COMPOSE_PROFILES=gpu` in `.env`). Keep image names fully qualified (`docker.io/…`) and bind mounts `:ro,z` in the compose file — Docker ignores both, Podman needs them — and keep both GPU services working when editing it.

The worker needs the params and eval schemas too (`nomoscope-workflow init-param-db`, `nomokrisis-eval init-db`, idempotent; ordinary commands no longer apply them, they refuse to run without them). An existing legislation DB gets new `Nomotheca-RAG/db/migrations/*.sql` with `make migrate` (recorded in `schema_migrations`; a fresh volume starts with all recorded). `seed.sql` holds reference rows only; the old demo corpus is the opt-in `db/demo.sql`. Roles for a shared deployment are in `Nomergon-worker/db/roles.sql` (worker role, `nomos_reviewer` group, one login per analyst; the dev stack keeps the single `jrc` superuser).

Postgres is on host port **5434** (not 5432, to avoid clashing with a local PG). Default DB URL: `postgresql://jrc:jrc@localhost:5434/legislation`. pgAdmin admin@euromod.eu / admin.

Python packages use **`uv`**, as **one workspace with one lockfile**: the repo-root `pyproject.toml` lists the five packages and the root `uv.lock` pins them all — the test suites and the worker image install from the same file (five per-package locks drifted apart until 16 Nov 2026). `uv sync --all-packages` (plus `--extra embeddings` for the local encoder) fills the one `.venv` at the repo root; a plain `uv sync` inside a package is exact and would strip the others' dependencies. Run commands with `uv run` from inside each package dir:

```bash
# Ingest (Nomotheca-RAG/ingest)
uv run python -m nomotheca_ingest.cli tui                 # interactive Textual ingestion monitor
uv run python -m nomotheca_ingest.cli fr instrument JORFTEXT000051168007
uv run python -m nomotheca_ingest.cli country-report FR ../country_reports/Y16_CR_FR.md   # non-legislative corpus
uv sync --extra embeddings                              # manual path only: cli embeddings build --backend torch|openvino
                                                        # normally: `cd Nomergon-worker && uv run nomergon submit embed --wait` (only chunks lacking a vector)
uv sync --extra embeddings --extra translate            # manual path only: cli translate run --model openrouter/...
                                                        # normally: `nomergon submit translate --wait --payload '{"model": "…"}'` (worker holds the keys)

# Agentic workflow (Nomoscope-agentic-workflow/pipeline) — the worker runs these; a developer can too
uv run nomoscope-workflow run-targets group:FR:tinkt_fr:tin_schedule 'euromod://FR/tin_fr/def_const/$tinrt_cdhr' --year 2025 --model mock/extractor
                                                        # records come straight from the params DB; one run = one system year
uv run nomoscope-workflow run-country FR --year 2025 --model mock/extractor   # every parameter of a country
                                                        # both run commands skip parameters EUROMOD holds as n/a (or holds nothing for)
                                                        # in that year — ~1/3 of each country, superseded constants; --include-na runs them
uv run nomoscope-workflow queue                         # params.review_queue
uv run nomoscope-workflow export --out-dir /tmp/export  # the change set: one <CC>_changes.json per country

# Worker (Nomergon-worker) — in the container (`podman exec nomergon-worker-cdi /app/.venv/bin/nomergon …`) or on the host
uv run nomergon serve                                   # claims ops.jobs; needs the GPU env
uv run nomergon submit embed --wait                     # nightly batches, by hand: embed, then
uv run nomergon submit translate --wait --payload '{"model": "azure_openai/gpt-5.6-luna", "target_lang": "en"}'
uv run nomergon jobs; uv run nomergon events <id> --follow; uv run nomergon cancel <id>

# Validation UI (Nomoscope-agentic-workflow/ui)
npm install
npm run tauri dev                                       # WSL: prefix LIBGL_ALWAYS_SOFTWARE=1
# RAG chat (Nomoscope-agentic-workflow/rag-ui) — same commands; Vite on :5174

# Evaluation (Nomokrisis-evaluation_pipeline)
uv run nomokrisis-eval init-db                             # create eval schema
uv run nomokrisis-eval import-golden                       # seed a fresh database from the file-era fixtures (dataset/, golden_sources/)
uv run nomokrisis-eval build-openfisca-dataset --year 2025 --country FR  # draft cases from the OpenFisca corpus (selection in eval.golden_selections)
uv run nomokrisis-eval verify <case-id>                    # or the UI's "Golden set" tab (reviewer = current_user)
uv run nomokrisis-eval run --as-of 2025-06-01 --model mock/extractor   # offline smoke run (one progress line per case)
uv run nomokrisis-eval resume                              # continue an interrupted run, from eval.runs/run_cases/results
                                                           # run / run-benchmark / resume run -j 4 cases at once (EVAL_CONCURRENCY;
                                                           #   a case is ~all LLM wait; scout ingests and GPU builds stay serialised)
uv run nomokrisis-eval run-benchmark FR --year 2025 --model … --sample 20 --seed 1   # blind EUROMOD Y-1 -> Y over every parameter
uv run nomokrisis-eval run-benchmark panel --year 2025 --model …   # THE dataset for comparing models: 250 cases, 50 each of FR/ES/IE/LT/NL (`NL,` = one country's 50),
                                                           #   a fixed stratified draw (benchmark.build_panel)
uv run nomokrisis-eval benchmark-report <run-id>           # 'ready to accept' + 'wrong proposals' first, then the change matrix
uv run nomokrisis-eval report
```

Run a single test with `uv run pytest tests/test_cli.py::test_name` (or `-k pattern`). All packages set `pythonpath=["src"]` and `testpaths=["tests"]` in `pyproject.toml`.

## Debugging a workflow run from a Phoenix trace id

Given a trace id (or "why did this run fail?"), use the **`/debug-phoenix-trace`** skill ([.claude/skills/debug-phoenix-trace/SKILL.md](.claude/skills/debug-phoenix-trace/SKILL.md)): it inspects the trace's spans straight in the `phoenix` DB inside the shared Postgres container, cross-checks corpus/embedding coverage in the `legislation` DB, and lists the known failure modes. Rule of thumb: most `not_found` runs are corpus problems (act not ingested, or ingested but not yet embedded), not LLM problems.

## LLM provider configuration

Models everywhere are **provider-prefixed strings**: `anthropic/…`, `openai/…`, `azure_openai/…`, `openrouter/…`, `together/…`, `jrc/…` (JRC's own OpenAI-compatible gateway: `JRC_LLM_BASE_URL` + `JRC_LLM_API_KEY`, a distinct prefix on purpose so a run on the internal gateway is never confused with OpenAI proper when models are compared), plus `mock/…` for key-less demos and deterministic tests. **Keys exist on the worker only**; an analyst picks from the list the worker publishes (`ops.worker_models`, from `WORKER_MODELS`) and never types a model string or holds a key. **Nothing in the pipeline knows the provider** — endpoint flexibility is a hard contractual requirement (Activity 5 compares multiple LLMs). Provider access lives in the small workspace package `nomos-llm` ([nomos-llm/src/nomos_llm/providers.py](nomos-llm/src/nomos_llm/providers.py), plus the one `.env` loader in `nomos_llm/env.py`); `nomoscope_workflow.llm` re-exports it and adds the proposal/critique steps, the ingest translator uses `nomos_llm` alone (it no longer depends on the workflow), and `nomokrisis_eval` goes through the workflow. For `azure_openai/<name>` the name after the slash **is the Azure deployment**; `AZURE_OPENAI_DEPLOYMENT` is only a default for a bare `azure_openai`, never an override — it used to be one, and every `azure_openai/*` run between 5 Aug and 8 Sep 2026 (terra, nano-2, Mistral, DeepSeek, sol…) silently ran on the `gpt-5.6-luna` deployment, judge included. Azure deployments named `gpt-*` / `o<digit>…` go through the **Responses API** (`llm.uses_responses_api`): on `/chat/completions` gpt-6-luna refuses function tools while reasoning — and structured output is a function tool — and on `/responses` it refuses `temperature`, so `model_settings` (nomos_llm) is the one place request settings are built and drops it there; other Azure deployments (Mistral, DeepSeek) stay on chat completions. `eval.runs` records `resolved_model` / `resolved_critique_model`; before comparing two runs as two models, check those differ and that Phoenix's LLM spans (`attributes->'llm'->>'model_name'`) agree. OpenRouter requests carry `max_tokens` = `llm.ROUTED_MAX_TOKENS` (16 384): without it a fallback provider budgets the prompt against its own huge output reservation (GMICloud refused 88k-token MiniMax M2.7 prompts, 14 crashes in the 14 Nov 2026 LT benchmark), and a model listed in `llm.CONTEXT_WINDOWS` gets its retrieved chunks trimmed to fit (`prompts.fit_hits`: lowest-ranked hybrid hits first, never a chunk the proposal cites); an unlisted model is never trimmed. Non-OpenAI model comparison: [docs/jrc_models_benchmark.md](docs/jrc_models_benchmark.md).

**One config file: the repo-root `.env`** (template [.env.example](.env.example)). Every package's `load_config()` reads it and no other `.env`; the process environment wins; the worker container reads it through `env_file` and keeps the values it was **created** with — recreate it alone (`podman-compose --profile gpu-cdi up -d --no-deps --force-recreate worker-cdi`; `--no-deps`, or Postgres restarts and kills a running job) after editing. `WORKFLOW_MODEL` is the one default: `WORKFLOW_CRITIQUE_MODEL`, `EVAL_BUILDER_MODEL` and `EUROMOD_TRANSLATE_MODEL` fall back to it (`EVAL_CRITIQUE_MODEL` unset = the model under test judges itself), and the worker publishes it first, then `WORKER_MODELS`, as the pickers' list. If keys live elsewhere, `set -a; source path/to/.env; set +a` before the command. See [.env.example](.env.example) for all knobs.

## Key constraints when changing things

- **The workflow is export-first and human-gated.** Never make the pipeline write back into EUROMOD parameter files; accepted values are exported, and only after a human Accept in the UI. A queue item is keyed `<country>_<target>_<system year>` (`queue_store.item_id`, the primary key of `params.review_queue`), so re-running a year replaces its review instead of piling up near-duplicates — the UI collapses the remaining per-year runs to one row and navigates between them in the detail panel. Reviewed queue items are immutable to re-runs (unless `--force`); `params.review_decisions` is append-only and is the system of record for human decisions. **A decision the DB refuses fails outright**: `store::prepare_decision` computes the updated item and the audit entry, then ONE call to `params.decide_review_item()` inserts the audit row and updates the queue row in the same transaction, with `reviewer = session_user` (inside a SECURITY DEFINER function `current_user` is the owner). Never split that into two statements or write the item first. There is no local copy of anything.
- **The export back to EUROMOD is a change set, and analysts' metadata edits are rows (ADR 0005).** `params.euromod_change_set` is the one definition both exports read (UI `<CC>_changes_<date>.json`, CLI `<CC>_changes.json`). Per changed parameter it holds the net metadata edits `{field: {from, to, …}}` and only the value rows a human accepted as `changed`/`new` or edited; no history, no accepted `unchanged`. A UI edit goes through `params.edit_parameter()` only (validates `KNOWN_UNITS`/`SourceType` in SQL — a pytest keeps the lists in step; refuses identity and values), is appended to `params.parameter_edits`, and is re-applied last by `ingest-params` and `curate-params`, so it wins over the export and the YAML.
- **The workstation executes nothing; the worker executes everything (ADR 0004).** Never add a process spawn, a model load, an API key read or a data directory to the UI. A new kind of work is a `JobSpec` row in `nomergon/jobs.py` with a payload model owning `to_argv()`, the type added to the `ops_schema.sql` lists (a test compares them), `nomergon job-types --write` (the UI's `job_types.json`) and a UI submit; a CLI that has a result prints one `@result {json}` line last. The `ingest` payload is typed per sub-command; a document source must be an http(s) URL or a file under `WORKER_DOCUMENT_DIR` (unset = URLs only), so a reviewer cannot ingest a worker file. The reviewer role can read, decide, submit, cancel its own jobs and verify a golden case, nothing else (`Nomergon-worker/db/roles.sql`). Module-global latches (Tavily 432 in `web.py`, `query_encoder._disabled`) are reset because each job is a fresh subprocess; do not move job execution in-process.
- **An old amending provision is not the law in force** (prompt 0.14.0). Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **The verbatim-quote rule is mechanical, not prompt-only.** If you touch `propose`/`critique`, keep the character-for-character extract check against the cited chunk — it's the anti-hallucination guarantee.
- **Every instrument carries a source-trust class, and evidence retrieval excludes by class.** `instruments.source_trust_class` is `evidence` (legislation and statute-level acts), `guidance` (circulars, doctrine — citable, ranked equal, but shown as guidance on every proposal and counted in the eval) or `context` (never citable). Retrieval filters `source_trust_class <> 'context'` — never on an `instrument_type` string — and the class travels on every hit and citation. For a contributed document it is derived from the kind the reviewer states and never stated directly; "other" is guidance, so an unnamed document cannot be granted statute-level trust by accident. See [docs/adr/0001-guidance-is-citable-evidence-with-a-visible-class.md](docs/adr/0001-guidance-is-citable-evidence-with-a-visible-class.md).
- **Collective agreements are evidence, like the law** (ADR 0006). Where the social partners set a rate (FR AGIRC-ARRCO: ANI du 17 novembre 2017 art. 37, APEC, cadres' prévoyance), the agreement is the source of truth: `instrument_type='collective_agreement'`, class `evidence`. FR reads them from DILA **KALI** as source `FR-KALI` (`cli instrument fr KALITEXT…/KALIARTI…`). KALI exists only as dumps, so the adapter keeps a local copy under `NOMOTHECA_KALI_DIR` (worker volume `kali-cache`, ~1.8 GB), kept current by `cli kali-sync` (an ingest syncs on its own after 12 h), and archives each document as DILA JSON so the LEGI parser and `reparse` apply. The scout keeps `KALITEXT`/`KALIARTI` ids and refuses `KALICONT` (a whole convention). Contributed documents have a `collective_agreement` kind in every country. Board decisions that are not agreements (the AGS rate) are not covered.
- **The scout fetches guidance from listed publishers, always as guidance.** Some values are published by an administration, not in any act (the Cnav circular gives the ASPA/ASI ceilings after the 1 April revaluation). `scout_sources.GUIDANCE_PUBLISHERS` lists, per country, the publisher's domain, its fixed kind (FR: Cnav and Unédic `circulaire`, BOFiP `doctrine`) and a URL pattern for one document, which also gives the title and the validity date. No full date in the URL means no ingest. The model only writes `guidance_queries`, searched on those domains. A matching URL is ingested with `cli document … --kind <fixed> --trigger cache_miss`. An ingest test checks that every publisher kind maps to guidance, so a web-discovered document can never become evidence. How contributed documents are cut into sections, chained by edition and fetched: [Nomotheca-RAG/CLAUDE.md](Nomotheca-RAG/CLAUDE.md).
- **Country Reports are context, never evidence.** EUROMOD Country Reports are ingested with `instrument_type='country_report'` and `source_trust_class='context'`; Nomoscope's evidence retrieval SQL excludes them by that class (see the rule above), and `retrieval.country_report_search()` is the only sanctioned way to read them (query framing, UI display). Never let `propose`/`critique` cite a CR chunk — the CR describes the model, so citing it as support is circular.
- **`national_team_source` values route around the pipeline** and are never overwritten — not every EUROMOD parameter is legislation-derivable.
- **Regional acts are child jurisdictions, and retrieval is scoped by the parameter's region** (ADR 0003). Spain's autonomous-community acts are filed under `ES-AR`, `ES-CN`, … (`jurisdictions.parent_id = ES`, seeded from one table in `Nomotheca-RAG/ingest/src/nomotheca_ingest/countries/es/regions.py`; existing databases run `db/migrations/0002_es_autonomous_communities.sql`). Evidence retrieval filters on a jurisdiction *scope* — `[country]` for a national parameter, `[country, region]` for a regional one, the region read off the constant's NUTS-2 digits by `regions.region_key` (`$bsarg_rg24_*` → `ES24` → `ES-AR`) — never on the whole tree: Aragón's parameter must not be "supported" by a verbatim quote from Asturias's decree, a false positive the extract check cannot catch. Regional citations are qualified by region (`Ley 3/2021 Asturias Artículo 14`; Aragón has a Ley 3/2021 too), and `EsResolver` refuses a bare regional number. BOE consolidates the communities' framework laws but not their annual budget laws, where the current amounts live — see `.scratch/es-autonomous-communities/`.
- **Percent literals are scalars in the store, and units outside the export vocabulary exist on purpose.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **A derived value is arithmetic over quoted operands, checked like an extract.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **An "FYA" amount is proposed as the amount in force, never averaged.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **Confirming the held value is not blocked by its date.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **A system year is the whole year.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **A code article is held with its recent versions, and its cross-references are followed.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **Retrieval also searches recent texts for the figure EUROMOD holds.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).

- **A mistyped `citation_chunk_id` is resolved by its extract, never guessed.** Details: [Nomoscope-agentic-workflow/CLAUDE.md](Nomoscope-agentic-workflow/CLAUDE.md).
- **The parameter store is the source; nothing is materialized to disk.** `extracted_parameters/enriched/<CC>.enriched.json` is the EUROMOD-delivered ground truth and is read-only; everything else the DB needs arrives through the same `ingest-params` + `curate-params` path — the curation overlay `Nomoscope-agentic-workflow/pipeline/curation/<CC>.curation.yaml` carries what the export lacks or gets wrong (`temporal_basis`, `source_type`, and `unit`: the FR export labels all 146 `*rate*` parameters `currency`, IE 48 and LT 54 rate-like parameters likewise, all curated to `/1` — membership by value, every year's value a fraction — because the prompt's percent normalisation and the critique's range check key on it), re-applied after every `ingest-params` — `extracted_parameters/curated/<CC>.in_function.json` for parameters EUROMOD defines inside functions (the connector cannot export them; FR CDHR), and the export's own `groups` block for bracket schedules, reassembled into one record by `paramdb.load_group_record` (FR barème = `FR:tinkt_fr:tin_schedule`). `run-targets` and a golden case load the record straight from the DB (`paramdb.load_record` / `load_group_record`) — never let a run or a golden case depend on a hand-authored parameter file.
- **The golden set is rows, keyed by content hash.** Details: [Nomokrisis-evaluation_pipeline/CLAUDE.md](Nomokrisis-evaluation_pipeline/CLAUDE.md).
- **Golden readiness follows the value-bearing citation, and a golden citation list is any-of.** Details: [Nomokrisis-evaluation_pipeline/CLAUDE.md](Nomokrisis-evaluation_pipeline/CLAUDE.md).
- **OpenFisca corroborates, it never evidences.** The ingested OpenFisca corpus (`params.external_*`, commit-pinned) is a *curated secondary source*: it can suggest links (`nomoscope-workflow match-openfisca` → `params.parameter_links`, suggestions until `validated_by` is set) and draft evaluation ground truth (`nomokrisis-eval build-openfisca-dataset` → `verified: false` cases reviewed in the UI's Golden set page, under expert tools), but it can never be a `supporting_extract` for a proposal. Golden cases re-derive the expected value from the parameter's `temporal_basis`, not from the link's year alignment: `income_year` → the OpenFisca value keyed `<system year>-01-01` (the same income-year convention the pipeline back-dates to), `in_force` → the value in force at `as_of`. OpenFisca stores change points only, so "the value at D" is always the latest entry at or before D.
- **`temporal_basis: income_year` parameters (FR income-tax family) are searched under the law's income-year label.** EUROMOD system year Y holds the schedule enacted by the finance act for Y and applies it to the incomes of Y (FR_2025: loi n° 2025-127, the PLF 2025, on 2025 incomes); French law and OpenFisca label that same schedule by the income it is legally assessed on, one year earlier («impôt 2025 sur les revenus 2024»). So **for system year Y the value is in the text the law labels "income Y−1"** — a rule for finding the text, not a statement about which incomes EUROMOD taxes; the mapping lives in exactly one place, `schema.income_year_for` (offset `INCOME_YEAR_OFFSET = -1`), and four things derive from it: retrieval/scout target 1 July of the year *after* the income year, proposals back-date `valid_from` to the income-year start, the critique's budget-act window opens 1 December of the income year (older versions route `provisional` — Accept is blocked in the UI; distinct from `not_found` — **unless** the cited text is a consolidated code article in force on the retrieval date with a corpus snapshot at least that fresh: that is the text the assessment of income year Y applies, however old its version start — CGI art. 197 «en vigueur du 16 février 2025 au 21 février 2026» is the 2024-income barème, art. 223 sexies has read the same since 2018 — decided by `pipeline._consolidated_in_force`, guarded against a text whose application note names the *next* income year), and golden cases read the OpenFisca entry at `income_year_for(year)-01-01`. Never re-derive `as_of.year ± 1` at a call site. A third basis, `start_of_year`, is for parameters EUROMOD holds at their 1 January value (`schema.start_of_year_as_of`): retrieval, the critique's date check and the prompt use 1 January of the system year, and no later-in-year version is added — FR `$tpr_threshold*` (CGI 1417 is revised each June), `$UB_dayfixamt` (each 1 July), `$tscerui_rate1`, `$bsawk_income_rate`, each proven on EUROMOD's own history (a change in year Y first appears in system year Y+1). Note the FR Country Report's Table 2.77 heads its column "Taxation 2025 (income 2025)" — that label is wrong as a statement of French law: its values are the barème for 2024 income (taxation 2025, LF 2025). It is only true in the sense that EUROMOD applies them to 2025 incomes. The flag itself is curated (JSON `information` block + `params.parameters.temporal_basis`, preserved by re-ingest) — never derive it from the export, and don't let legal in-force dates in the legislation DB be rewritten to compensate.
- **Value scoring must normalise, not string-match.** Details: [Nomokrisis-evaluation_pipeline/CLAUDE.md](Nomokrisis-evaluation_pipeline/CLAUDE.md).
- **Embeddings are normally an `embed` job, not a hand-run command.** After an ingest, `reparse`, `rechunk` or translation, `uv run nomergon submit embed --wait` (in `Nomergon-worker`; payload `model_id`, `batch_size`, `limit`, `dry_run`, `precision`, `authentic_only`) embeds exactly the chunks with no vector for that model, on the worker's GPU. The `cli embeddings build` commands below are the manual path (no worker, debugging, `--in-force-on` comparison builds); never run one while the worker is embedding or an eval is running — one GPU.
